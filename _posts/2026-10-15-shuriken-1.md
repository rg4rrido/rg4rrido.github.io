## Introducción

En esta máquina de VulnHub, **Shuriken:1**, realizaremos una auditoría de seguridad en un entorno controlado, recorriendo las distintas fases de reconocimiento, enumeración, explotación y escalada de privilegios. Durante el proceso, aprovecharemos vulnerabilidades como **LFI**, la subida de archivos en ClipBucket y el abuso de *wildcards* en tareas *cron* para obtener acceso inicial al sistema y alcanzar privilegios de *root*.

### Explotación de **LFI**

En este punto lo primero en que deberíamos pensar es en un posible **LFI**.

```http
http://shuriken.local/index.php?referer=/etc/passwd
```

```bash
curl -s -X GET "http://shuriken.local/index.php?referer=/etc/passwd"
```

![Explotación de **LFI**](/assets/img/posts/2026-10-15-shuriken-1/17-explotacion-de-lfi.png){: width="600" }

Y efectivamente, logramos explotar un **LFI** y obtener el contenido del archivo */etc/passwd*. Gracias a esto, obtenemos el usuario válido del sistema, “server-management”, con el que podríamos tratar de iniciar sesión en los paneles de autenticación lanzando un ataque de fuerza bruta.

#### Uso de wrappers para obtener código fuente de la web

Antes de eso vamos a tratar de ver el código fuente del index.php; para ello podríamos apuntar directamente al recurso index.php, pero esto entraría en bucle y podría saturar el servicio web. Para evitar conflictos podríamos hacer uso de wrappers, en concreto del wrapper *php://filter*, que permite aplicar un filtro (como una conversión) a un recurso al que apunte.

```bash
curl -s -X GET "http://shuriken.local/index.php?referer=php://filter/convert.base64-encode/resource=index.php"
```

![Uso de wrappers para obtener código fuente de la web](/assets/img/posts/2026-10-15-shuriken-1/18-uso-de-wrappers-para-obtener.png)

Al pasarle el script *php* de esta forma no lo interpreta y nos lo muestra en *base64*, de forma que podemos decodificarlo en nuestra máquina para ver su contenido.

```bash
echo -n "cadenaBase64" | base64 -d; echo
```

De esta manera logramos ver el contenido del archivo con el código *php* sin interpretar.

#### ¿Función str_replace para sanitizar potencial **LFI**?

Al final del archivo vemos lo siguiente:

![¿Función str_replace para sanitizar potencial **LFI**?](/assets/img/posts/2026-10-15-shuriken-1/19-funcion-strreplace-para-sanitizar-potencial.png){: width="500" }

Ahí es donde está configurado el parámetro “referer” que hace referencia a un archivo y se le está aplicando una pequeña sanitización con la función *str_replace*. Utilizar esta función para tratar de sanitizar código contra posibles **LFI** no es muy buena práctica, ya que su función es sustituir lo que indique, en este caso “../”, por el segundo argumento que se indique, en este caso por nada, es decir, lo omite.

*¿Cuál es el problema real?* Pues que esta función no aplica la sustitución de forma recursiva y se queda en el primer match, de forma que podríamos bypassearla muy fácilmente:

![¿Función str_replace para sanitizar potencial **LFI**?](/assets/img/posts/2026-10-15-shuriken-1/20-funcion-strreplace-para-sanitizar-potencial.png){: width="800" }

Por lo que queda claro que no es muy buena práctica utilizar esta función para este propósito.

### Detección de tareas *Cron* de forma manual

Después de probar varios vectores comunes como permisos suid, capabilities, etc., decidimos probar a detectar tareas *cron* (tareas que se ejecutan a intervalos regulares de tiempo), pero esta vez de forma manual, creando un script de bash que las detecte (en vez de utilizar la herramienta [pspy](https://github.com/DominicBreuker/pspy)). Para ello podemos utilizar este script de bash:

```bash
#!/bin/bash

old_process=$(ps -eo user,command)

while true; do
	new_process=$(ps -eo user,command)
	diff <(echo "$old_process") <(echo "$new_process") | grep "[\>\<]" | grep -vE "procmon|command|kworker"
	old_process=$new_process
done
```

Con este script estaríamos continuamente comparando los comandos en ejecución en el sistema y nos mostraría con un ">" los nuevos comandos en comparación a los últimos registrados en la variable "$old_process", y con un "<" los que ya no se estén ejecutando. Lo ejecutamos y detectamos lo siguiente:

![Detección de tareas *Cron* de forma manual](/assets/img/posts/2026-10-15-shuriken-1/42-deteccion-de-tareas-cron-de.png){: width="1000" }

Al parecer se está ejecutando una tarea *cron* que ejecuta el script “backupsrv.sh”, podemos revisarlo en el archivo */etc/crontab*.

![Detección de tareas *Cron* de forma manual](/assets/img/posts/2026-10-15-shuriken-1/43-deteccion-de-tareas-cron-de.png){: width="800" }

Podemos echar un vistazo al script:

![Detección de tareas *Cron* de forma manual](/assets/img/posts/2026-10-15-shuriken-1/44-deteccion-de-tareas-cron-de.png){: width="400" }

Este script lo que hace es coger todos los archivos del directorio */home/server-management/Documents* empleando una *wildcard* `*` y el comando `tar` para comprimirlos y ejecutar el backup en la ruta destino.

### Abusando de **Wildcards** (tar command)

*¿Cuál es el problema de esto?* El riesgo está en que, al estar utilizando *wildcards*, al ejecutar el backup se va a incluir todo lo que haya en la ruta indicada, de forma que se podría dar este caso:

![Abusando de **Wildcards** (tar command)](/assets/img/posts/2026-10-15-shuriken-1/45-abusando-de-wildcards-tar-command.png){: width="500" }

Al hacer uso de *wildcards*, el riesgo está en que un atacante puede crear archivos con nombres de parámetros para que así el comando que se esté ejecutando los interprete como tal. Y el comando `tar`, si consultamos de nuevo [gtfobins](https://gtfobins.org/), podemos ver que se puede spawnear una *shell* con él.

![Abusando de **Wildcards** (tar command)](/assets/img/posts/2026-10-15-shuriken-1/46-abusando-de-wildcards-tar-command.png){: width="600" }

Haciendo uso de los parámetros `--checkpoint=1` y `--checkpoint-action=exec=/bin/sh`, sabiendo esto podríamos crear en el directorio */home/server-management/Documents* los siguientes archivos:

```bash
cd  /home/server-management/Documents
touch -- --checkpoint=1
touch -- --checkpoint-action=exec='sh command'
```

![Abusando de **Wildcards** (tar command)](/assets/img/posts/2026-10-15-shuriken-1/47-abusando-de-wildcards-tar-command.png){: width="700" }

Esto lo que hará es que, cuando se ejecute la tarea cron con privilegios de root, al estar utilizando la *wildcard* cogerá los nombres de dichos archivos como parámetros y ejecutará el contenido del script “command”, por lo que podemos crear ese archivo con el siguiente contenido:

```bash
#!/bin/bash
chmod +s /bin/bash
```

Por lo que, cuando se ejecute la tarea *cron* e interprete los archivos como parámetros por el empleo de la *wildcard*, a su vez se ejecutará el script malicioso y se otorgarán privilegios *suid* a la bash. Podemos monitorizar en tiempo real cuando suceda con el siguiente comando:

```bash
watch -n 1 ls -l /bin/bash
```

![Abusando de **Wildcards** (tar command)](/assets/img/posts/2026-10-15-shuriken-1/48-abusando-de-wildcards-tar-command.png){: width="500" }

![Abusando de **Wildcards** (tar command)](/assets/img/posts/2026-10-15-shuriken-1/49-abusando-de-wildcards-tar-command.png){: width="500" }
